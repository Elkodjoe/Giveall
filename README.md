# Giveall — Relationship Fitness / Love OS

A 90-second daily relationship fitness app. See `docs/00-product-overview.md` for the full product spec (onboarding flow, rules-engine decision matrix, power-ups) — start there before touching code.

## What's here

- `docs/` — designer/dev handoff spec: onboarding flow copy + rationale, the Love OS decision matrix, power-up prompts and copy rules.
- `src/engine/` — the rules engine as plain TypeScript, no React/RN dependency. Unit-tested (`src/engine/__tests__`). This is the reusable "brain" — safe to lift into a backend later if logic needs to move server-side.
- `src/data/` — onboarding question banks (attachment scenarios, love language forced-choice pairs).
- `src/components/`, `src/state/` — RN UI pieces for the onboarding flow.
- `app/` — Expo Router screens: Onboarding Screens 1–6, plus `checkin.tsx` (daily 90-second check-in), `bids.tsx` (Bid Tracker), `curiosity.tsx` (Curiosity Card), `memory-vault.tsx`, `desire-inventory.tsx`, `settings.tsx`, and `partner.tsx` (double opt-in Partner Mode).
- `src/firebase/` — Firestore document types, security rules-matching collection helpers, and auth. Works without a Firebase project configured — see `docs/06-firebase-provisioning.md`.

## Getting started

```bash
npm install
npm run start   # opens Expo dev tools; press i/a/w for iOS/Android/web
npm test        # runs the engine unit tests
```

## Status

Onboarding flow (Screens 1–6), daily check-in, Bid Tracker, and Curiosity Card screens are all built, running the full rules engine (decision matrix, bid tracker, curiosity ladder, recalibration, appreciation prompt builder, retention notification copy), unit-tested, and **verified end-to-end against a real, live Firebase project** (`giveall-app`) — not just the client-only demo path. Firestore database, security rules, indexes, Anonymous Auth, seed data, and a registered web app are all deployed; `.env` is populated. See `docs/06-firebase-provisioning.md` for exact status and a real security-rules bug that deployment surfaced and got fixed (create-vs-read rule split for user-owned collections). Everything still degrades gracefully to client-only if Firebase isn't configured (e.g. a fresh clone with no `.env`).

The Appreciation Generator (`src/engine/appreciationGenerator.ts`'s prompt, wrapped by `functions/src/generateAppreciation.ts`) supports both Anthropic and OpenAI with automatic fallback — only one API key needs to be configured. Since Cloud Functions aren't deployed (Blaze deferred), `app/payoff.tsx` also tries `src/llm/ollamaClient.ts` — a direct client-side call to a locally running Ollama server, letting the generator be tested live for free without billing or an API key. Order: Cloud Function → Ollama → static fallback line, always rendering the fallback instantly first. **Verified working end-to-end with a real local model** (`llama3.2:3b`) — genuinely live-generated appreciation text, not a canned example.

`app/payoff.tsx`'s "Save it" / "Send it" CTAs — `docs/01-onboarding-flow.md` Screen 5's "instant value delivered before any ask" moment — used to both just navigate on, discarding the shown appreciation line. Both now log it to `action_logs` (best-effort); "Send it" also invokes RN's native `Share.share()` so the user can genuinely send it to their partner. Verified live: real `action_logs` docs landed in `giveall-app` for both buttons, with no new console errors from the `Share` call on web, then cleaned up.

**Cloud Functions are written but not deployed** — `nightlyRecalculateWeights`, `activatePartnership`, `validateProfile`, and `generateAppreciation` all need the Blaze billing plan, deliberately deferred (needs a payment method the user isn't ready to add). Nothing in the app breaks without them.

Two more previously-dead pieces closed in this pass:
- `scripts/seed/suggested_actions.json` — the "content-managed catalog" — used to be seeded and typed but never fetched; `decisionMatrix.ts` silently duplicated its copy by hand instead, so editing the seed JSON did nothing. `app/checkin.tsx` now fetches it and joins it against `MicroAttunement.actionId` (`resolveActionCopy()` in `src/engine/decisionMatrix.ts`), falling back to the hardcoded copy when Firestore isn't available. Verified live by temporarily marking a real seed doc's text in `giveall-app` and confirming it rendered on-screen.
- `getDailyCheckinsLastNDays()` had zero callers anywhere despite `daily_checkins` being written every check-in. `app/settings.tsx` now shows a "Your Last 7 Days" trend card (avg Seen/Safe/Sought/Mood + days logged) via a new pure `averageCheckins()` helper (`src/engine/scale.ts`). Verified live with 7 real days of seeded data rendering correctly, then cleaned up.

**Two real `firestore.rules` bugs found and fixed** by testing the deployed rules directly against `giveall-app` with real two-user (custom-token) sessions — the Admin SDK used for every other verification in this project bypasses rules entirely, so these could only surface this way. See `docs/04-firebase-schema.md`'s `partnerships` entry for the full writeup:
1. The `/profiles` partner-read rule built the partnership lookup id unsorted (`reader_uid + '_' + owner_uid`), while the doc is actually stored at the two uids sorted — silently breaking partner-read for roughly half of all uid pairings, undetectably, since it "worked" whenever the reader's uid happened to sort first.
2. The `partnerships` `optIns` update/create rules restricted which *field* could change but not which *key inside the map* — either party could unilaterally write the *other* party's opt-in to `true`, fabricating consent and fully defeating "double opt-in" (the exact privacy promise `app/settings.tsx` makes).

Both fixed with small rules functions (`partnershipDocId()`, `otherPartner()`), deployed, and verified live: the spoofing writes now return `permission-denied`, the legitimate flow still works end-to-end, and profile-read now succeeds regardless of uid sort order.

**A third rules bug, found the same way, across a wider blast radius**: every user-owned collection (`daily_checkins`, `action_logs`, `bids`, `memory_vault`, `curiosity_card_progress`, `desire_inventory`) let an update also change the doc's `userId` field — so a user could create a doc as themselves, then reassign it to a victim, planting fabricated data into that victim's own reads (worst case: `action_logs` feeds the client-side recalibration logic, so this could manipulate another user's stored love language). Fixed with a shared `ownedByMeAndUnchanged()` rules function pinning `userId` across every update; verified live that the hijack write now returns `permission-denied` while the app's real update pattern (partial field updates, never touching `userId`) still works. See `docs/04-firebase-schema.md` for the full writeup.

`curiosity_cards` had the identical dead-catalog problem — seeded, typed, but `app/curiosity.tsx` only ever showed prompt text from the hardcoded `CARDS` array in `src/engine/curiosityLadder.ts`. It now fetches the current tier's cards via `getCuriosityCardsForLevel()` (new `levelForTier()` maps tier → catalog level) and prefers the live `question` text by id, falling back to `CARDS` otherwise. Verified live the same way as `suggested_actions`: marked a real seed doc, confirmed it rendered, restored it.

`app/memory-vault.tsx` is what makes `decisionMatrix.ts`'s "Recall Detail" prescription (triggered when `seen_score` is lowest) actually personal instead of falling back to a generic prompt — `app/checkin.tsx` now fetches real entries and marks one used per the same "first unused" selection the engine's `nextUnused()` makes internally. `app/desire-inventory.tsx` does the same for the "sought" axis ("Specific Desire + Play") — this collection had *no schema, rules, or helpers at all* before this pass, despite the engine depending on it since the original scaffold. `app/settings.tsx` ships the privacy guardrail copy from `docs/03-power-ups.md` #3 verbatim, plus a "delete my Memory Vault" action — both were previously unbuilt despite that doc calling the copy "not decorative." `app/partner.tsx` implements the double opt-in linking (share your own uid as a connection code, enter your partner's) that `firestore.rules`/`collections.ts` already had schema and helpers for but no UI ever used. All verified end-to-end against the live project — including Partner Mode with two separate simulated users in isolated browser contexts. Real bugs found and fixed this way: a missing Firestore composite index for the Memory Vault's unfiltered list query, and a `firestore.rules` bug where reading a not-yet-existing `partnerships` doc (checking "has my partner requested?") was always denied because `resource` is `null` before the doc exists and `resource.data.users` threw — same root-cause class as the create-vs-read bug above, this time on read.

`src/notifications/` (`checkinReminder.ts` + pure helper `nextOccurrence.ts`) finally wires up `docs/03-power-ups.md` #2's "retention that doesn't nag" rule as real local notifications via `expo-notifications`, instead of the copy rules just living in `retentionNotifications.ts` unused. `app/ritual-time.tsx` schedules the first reminder when onboarding picks a check-in time; `app/checkin.tsx` reschedules tomorrow's with a real 7-day Bid Response percentage when the data exists, else the neutral fallback line — never a fabricated "your partner felt..." claim, since no feedback mechanism produces that data. No-ops (not throws) on platforms without local notification support, e.g. Expo web.

`action_logs` — the collection `docs/02-love-os-brain.md` #3's dynamic recalibration ("the moat") depends on — had schema, security rules, and a nightly-recalculation Cloud Function all written, but nothing ever wrote to it: no screen called `logAction()`. `getMicroAttunement()` now returns a `loveLanguageType` + `actionId` per prescription (hand-matched to `scripts/seed/suggested_actions.json`'s equivalent entries — the values decisionMatrix.ts's hardcoded copy was already silently duplicating), and `app/checkin.tsx` adds a "Did this land?" 5-point reaction that logs it.

The client-side half of recalibration is now wired too: `src/engine/recalibration.ts`'s `checkRecalibration` + a new `toDailyFeedback()` reducer run in `app/checkin.tsx` after each reaction, and on a 5-day consistent contradiction the exact "We learned you feel more loved by X..." copy from `docs/02-love-os-brain.md` surfaces on-screen, `profiles.loveLanguageReceive` updates, and an append-only `recalibration_events` doc records it (new Firestore rule, deployed). This is a simpler client-side path running independently of the still-undeployed nightly EMA job. **Verified live end-to-end against `giveall-app`**: seeded 4 days of contradicting signal via the Admin SDK, a real 5th check-in flipped the stored love language and produced the audit doc, both confirmed read back and cleaned up.

**First real UX pass**: drove the full flow via Playwright at an actual phone viewport (390×844) and looked at the screenshots, not just the DOM/text — a different failure mode than the structural checks used everywhere else in this README. Found and fixed three real issues: (1) `app/payoff.tsx`'s "Your First Win" card used `flex: 1`, stretching it to fill the whole remaining screen height and leaving a large dead-looking empty gap below the appreciation text on onboarding's climactic "Aha moment" screen — now sized to content and vertically centered. (2) `app/checkin.tsx`'s action card showed raw internal engine terms directly to the user ("Axis: safe · Tone: plain, direct") — removed. (3) `app/partner.tsx`'s connection code (a 28-character uid meant to be shared between two people) had no copy button, and its "both opted in" status message leaked developer-facing text ("Cloud Functions aren't deployed yet; see docs/06-firebase-provisioning.md") straight into the UI — added a `expo-clipboard`-backed "Copy code" button and replaced the leaked status copy with plain user-facing language. All three verified live with before/after screenshots.
