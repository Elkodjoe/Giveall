# Giveall — Relationship Fitness / Love OS

A 90-second daily relationship fitness app. See `docs/00-product-overview.md` for the full product spec (onboarding flow, rules-engine decision matrix, power-ups) — start there before touching code.

## What's here

- `docs/` — designer/dev handoff spec: onboarding flow copy + rationale, the Love OS decision matrix, power-up prompts and copy rules.
- `src/engine/` — the rules engine as plain TypeScript, no React/RN dependency. Unit-tested (`src/engine/__tests__`). This is the reusable "brain" — safe to lift into a backend later if logic needs to move server-side.
- `src/data/` — onboarding question banks (attachment scenarios, love language forced-choice pairs).
- `src/components/`, `src/state/` — RN UI pieces for the onboarding flow.
- `app/` — Expo Router screens: Onboarding Screens 1–6, plus `checkin.tsx` (daily 90-second check-in), `bids.tsx` (Bid Tracker), `curiosity.tsx` (Curiosity Card), `memory-vault.tsx`, `desire-inventory.tsx`, `settings.tsx`, and `partner.tsx` (double opt-in Partner Mode).
- `src/firebase/` — Firestore document types, security rules-matching collection helpers, and auth. Works without a Firebase project configured — see `docs/06-firebase-provisioning.md`.
- `src/i18n/` — 7-language i18next setup (`locales/*.json`); see `docs/07-internationalization.md`.

## Getting started

```bash
npm install
npm run start   # opens Expo dev tools; press i/a/w for iOS/Android/web
npm test        # runs the engine unit tests
```

**Two real `firestore.rules` bugs found and fixed** by testing the deployed rules directly against `giveall-app` with real two-user (custom-token) sessions — the Admin SDK used for every other verification in this project bypasses rules entirely, so these could only surface this way. See `docs/04-firebase-schema.md`'s `partnerships` entry for the full writeup:
1. The `/profiles` partner-read rule built the partnership lookup id unsorted (`reader_uid + '_' + owner_uid`), while the doc is actually stored at the two uids sorted — silently breaking partner-read for roughly half of all uid pairings, undetectably, since it "worked" whenever the reader's uid happened to sort first.
2. The `partnerships` `optIns` update/create rules restricted which *field* could change but not which *key inside the map* — either party could unilaterally write the *other* party's opt-in to `true`, fabricating consent and fully defeating "double opt-in" (the exact privacy promise `app/settings.tsx` makes).

Both fixed with small rules functions (`partnershipDocId()`, `otherPartner()`), deployed, and verified live: the spoofing writes now return `permission-denied`, the legitimate flow still works end-to-end, and profile-read now succeeds regardless of uid sort order.

**All three rules bugs from this project's history are now permanent regression tests, not just fixed-and-hoped**: every bug found by manual, one-off adversarial testing this session (the two above, plus the `userId`-reassignment bug across 6 owned collections) was previously only verified live once, by hand — nothing stopped a future rules edit from silently reintroducing any of them. `src/firebase/__tests__/firestore.rules.test.ts` (26 tests) now encodes each exact attack against a real local Firestore emulator via `@firebase/rules-unit-testing` (pinned to `3.0.4` — the latest major, `5.x`, requires `firebase@^12`, one major ahead of this project's `^10.12.0`; bumping the app's actual `firebase` dependency just to satisfy a test tool's peer range wasn't worth the real-SDK-behavior risk). Run via `npm run test:rules` (wraps the file with `firebase emulators:exec`, needs Java — already present in this environment for the emulator's JVM). Deliberately **not** part of the default `npm test`, since that must keep working with no emulator running, which is what every other verification pass in this project relies on. One real infra quirk hit and fixed along the way: calling `ctx.firestore()` twice within the same `withSecurityRulesDisabled()` callback (once per collection touched) intermittently threw `Firestore has already been started and its settings can no longer be changed` in this exact SDK combination — fixed by capturing one `db` reference and reusing it, not a rules problem.

## Accessibility

A real screen-reader pass across every screen — not just the i18n string coverage. `src/components/ScoreSelector.tsx` (the 1-10 dot picker used four times on the check-in screen) previously exposed 10 individually-focusable, unlabeled dots with no way for a screen reader to know the current value; it's now one `accessibilityRole="adjustable"` element (renders as `role="slider"` on web, confirmed live) with a proper label and value, increment/decrement actions, and the individual dots hidden from the accessibility tree. Every `<Pressable>` across all 13 screens now has an explicit `accessibilityRole` (`"button"` for actions, `"link"` for in-app navigation), every toggle/chip (mood, bid type/response, memory type/sentiment, language switcher, ritual-time picker) reports `accessibilityState={{ selected }}`, every `TextInput` has an `accessibilityLabel`, and the emoji-only "Did this land?" reaction buttons (😞🙁😐🙂😍) get real translated labels ("Landed well", not just the raw emoji glyph, which VoiceOver/TalkBack would otherwise announce with an English, non-semantic name regardless of app language) — verified live that the correct label renders per button.

**Follow-up pass: color contrast and touch targets**, formally audited against WCAG 2.1 AA this time (computed actual relative-luminance contrast ratios for every token pair, not eyeballed):
- `colors.textSecondary` (used for captions/secondary copy app-wide) was `#8C7E77`, only 3.72:1 against `colors.background` — below AA's 4.5:1 minimum for normal-size text. Darkened to `#776B65` (5.15:1+ against every surface color it's used on), a small enough shift to be visually a non-event. Verified live: the new computed color renders on the deployed check-in screen.
- `src/components/ScoreSelector.tsx`'s 12px-tall score dots had only a 4px `hitSlop`, ~20px effective — well under the 44pt minimum (WCAG 2.5.5 / iOS HIG). Expanded to a 16px vertical `hitSlop` (44px total), kept tight horizontally so adjacent dots (6px apart) don't steal each other's taps. **Native-only**: live DOM inspection confirmed react-native-web doesn't implement `hitSlop` at all — the dot's click-testable box on web stays exactly 12px, unchanged — so this fix only takes effect in the real iOS/Android builds, the same class of platform gap already noted below for `accessibilityValue`.
- **Brand color darkened for AA compliance, applied everywhere**: `colors.primary` (`#FF6B5B`, the core brand coral) failed AA in its two most common uses — CTA-button background under white text (2.80:1) and ~15 inline link/kicker text elements across every screen (2.66-2.80:1). Darkened to `#B34B40` (4.75:1+ in every role — text-on-background, text-on-surface, white-on-button), same hue family shifted toward rust/brick. Sent before/after screenshots for visibility since this is a real, visible brand shift, not a silent tweak. Applied consistently everywhere the old coral appeared: `src/theme/tokens.ts` (`primary`, `error` — the latter unused but kept in sync), `app.json`'s Android adaptive-icon background, the baked-in pixel color in `assets/images/icon.png`/`favicon.png` (regenerated via the same Playwright-screenshot technique used to create them originally — `assets/images/splash-icon.png` and `adaptive-icon.png` turned out to already be transparent-background/white-glyph, confirmed via live pixel-alpha inspection, so they needed no change), and the `--primary`/`--primary-dark`/`--error` CSS variables in both `marketing/public/index.html` and `dashboard/public/index.html` (redeployed, contrast re-verified live on both). `tsc --noEmit` clean, 67/67 Jest passing throughout.
- **Chip touch targets fixed too**: mood (`checkin.tsx`), language switcher (`settings.tsx`), bid type/response (`bids.tsx`), and memory type/sentiment (`memory-vault.tsx`) chips all shared the same `paddingVertical: 8` (~34px tall). Bumped to `12` (~42px, measured live via a real bounding-box check on the deployed check-in screen — close enough to the 44px guideline that further micro-tuning wasn't worth it). Unlike the `ScoreSelector` dots above, this is a real layout-size change (not `hitSlop`), so it actually helps the web target too, not just native.

**Separately confirmed** (not a bug, a known react-native-web limitation): `accessibilityValue={{min,max,now}}` on `ScoreSelector`'s slider doesn't map to `aria-valuemin`/`aria-valuenow`/`aria-valuemax` on the web target, even though `accessibilityRole="adjustable"` correctly maps to `role="slider"`.
